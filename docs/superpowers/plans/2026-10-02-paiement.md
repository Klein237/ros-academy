# Paiement (formule pro) — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** un étudiant passe en formule `pro` en s'abonnant (9 € / mois, résiliable à tout moment) depuis « Mon compte » ; tant que l'abonnement est actif, son lab n'a plus de limite de minutes et son conteneur reçoit 2 vCPU / 4 Go. À la fin de l'abonnement, il repasse en `free`.

**Architecture :** Stripe est branché sur le service Comptes, sans SDK (API REST appelée avec httpx, comme GitHub et Google) :

- **Souscription** : `POST /compte/abonnement/souscrire` crée une session Stripe Checkout (`mode=subscription`, le prix `STRIPE_PRICE_ID`, `client_reference_id` = l'id du compte) et redirige vers la page de paiement hébergée par Stripe. Aucune donnée de carte ne passe par la plateforme.
- **Gestion** : `POST /compte/abonnement/gerer` ouvre le portail client Stripe (carte, factures, résiliation).
- **Vérité = Stripe** : `POST /api/comptes/stripe/webhook` vérifie la signature (`Stripe-Signature`, HMAC SHA-256, 5 min de tolérance), ignore les événements déjà traités, puis **relit l'abonnement auprès de l'API Stripe** avant de mettre à jour la formule : l'ordre d'arrivée des événements ne compte donc pas.
- La formule entre dans le JWT du lab (`plan`) à chaque ouverture via `/compte/lab` : le Hub applique les limites `pro` au démarrage suivant.

**Tech Stack :** service Comptes existant (FastAPI, SQLAlchemy, Alembic, httpx), API Stripe (Checkout, Billing Portal, Subscriptions, Prices, webhooks).

**Spec :** [Plateforme de formation ROS 2 — Spec de design](https://claude.ai/code/artifact/e0a0510b-9545-459e-9c12-da51ca1898ba) — « Décisions clés » (modèle économique), « Sécurité, quotas et erreurs » (quotas par formule), sous-projet 5.

## Décisions (2026-10-02)

- **Abonnement mensuel**, 9 € / mois. Le prix vit dans Stripe (`STRIPE_PRICE_ID`) ; la page affiche le montant que Stripe renvoie.
- **Formule pro : minutes illimitées**, 2 vCPU / 4 Go (déjà dans `PLAN_MINUTES` et `hub/rosacademy_hub/quotas.py`). L'arrêt après 20 min d'inactivité reste.
- **Statuts Stripe → formule** : `active`, `trialing`, `past_due` → `pro` (Stripe retente le paiement pendant `past_due`) ; tout autre statut (`canceled`, `unpaid`, `incomplete`, `incomplete_expired`, `paused`) → `free`. Une résiliation prend effet à la fin de la période payée (Stripe garde `active` jusque-là).
- **Désactivé par défaut** : sans `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` et `STRIPE_PRICE_ID`, aucune mention de l'abonnement n'apparaît et les routes répondent 404.
- Une formule `pro` donnée à la main (base de données) n'est pas touchée par Stripe tant que le compte n'a pas d'abonnement.

## Global Constraints

- Webhook : signature vérifiée sur le corps brut, comparaison à temps constant, horodatage à ±300 s ; un événement déjà traité (id) n'a aucun effet ; jamais de confiance dans le contenu de l'événement pour la formule (relecture de l'abonnement).
- Écritures par cookie (`souscrire`, `gerer`) : en-tête `Origin` vérifié, comme le reste de Comptes.
- La clé secrète Stripe n'apparaît dans aucune page, aucun journal.
- Rien ne change pour un compte `free` sans Stripe configuré.

## Review Focus

1. **Signature du webhook** : refus sans en-tête, avec une mauvaise signature, un horodatage trop ancien ou un autre secret.
2. **Formule** : jamais `pro` sans abonnement relu chez Stripe dans un statut payant ; retour en `free` à la fin ; idempotence des événements.
3. **Rattachement** : l'abonnement est rattaché au compte par `client_reference_id` puis par le client Stripe (`customer`), jamais par l'adresse e-mail saisie chez Stripe.

### Task 1 : Modèle et migration

- `users` : `stripe_customer_id` (unique, nullable), `stripe_subscription_id`, `abonnement_statut`, `abonnement_fin` (fin de la période en cours), `abonnement_resilie` (résiliation programmée).
- `stripe_events(id, recu_le)` : événements traités.
- [ ] Migration Alembic `0002` ; le test de migrations compare toujours au modèle.

### Task 2 : Client Stripe et webhook

- `billing.py` : `StripeClient` (httpx, formulaire encodé, clé en `Authorization: Bearer`) : `create_checkout`, `create_portal`, `subscription`, `price` ; `verify_signature(payload, header, secret, now)` ; `apply_subscription(db, user, sub)` (statut → formule).
- Webhook : `checkout.session.completed` (rattache `customer` au compte de `client_reference_id`, puis relit l'abonnement), `customer.subscription.created|updated|deleted` (relit l'abonnement de ce client).
- [ ] Tests : signature (valide, absente, fausse, expirée, autre secret) ; idempotence ; ordre des événements indifférent ; statut → formule ; client inconnu ignoré.

### Task 3 : Pages

- `/compte/abonnement` : formule actuelle, prix (lu chez Stripe, mis en cache 1 h), bouton « S'abonner » ou « Gérer mon abonnement » ; après le retour de Checkout, « Paiement en cours de confirmation » tant que le webhook n'est pas arrivé.
- « Mon compte » : lien vers l'abonnement ; bandeau « Quota épuisé » du lab : lien « Passer en pro » quand Stripe est configuré.
- [ ] Tests : routes absentes sans configuration ; `Origin` vérifié ; redirection vers Checkout avec les bons paramètres (faux Stripe) ; portail ; page selon le statut.

### Task 4 : Intégration

- Compose / `.env.example` : `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID`.
- README : créer le produit et le prix dans Stripe, activer le portail client, déclarer le webhook `https://<domaine>/api/comptes/stripe/webhook` (événements ci-dessus), tester avec `stripe listen`.
- [ ] Vérification locale de bout en bout contre un faux Stripe (Checkout → webhook signé → formule pro → JWT `plan: pro` → limites du conteneur).
