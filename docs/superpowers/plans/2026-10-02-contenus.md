# Site de contenu, format des modules et éditeur de formations — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** l'administrateur crée et modifie des formations depuis la plateforme (cours, lab, exercice avec bug, QCM), les publie après vérification automatique, et l'étudiant suit le parcours « ROS 2 Fondamentaux » (5 modules portés des supports existants) depuis le site, avec l'exercice lancé et vérifié dans son lab.

**Architecture :** un service **Contenus** (Python, FastAPI + Jinja2) rend le site étudiant et l'espace d'administration à partir d'un dépôt Git de contenu. Deux branches : `brouillon` (ce que l'administrateur édite) et `publie` (ce que voient les étudiants). « Publier » valide le format, lance les tests des modules modifiés dans un conteneur `ros-lab` sans réseau, puis avance `publie`. Le dépôt vit dans un volume ; il peut être poussé vers un dépôt distant (`CONTENT_GIT_REMOTE`). Le Lab UI récupère les fichiers du module auprès du service Contenus et les écrit dans le conteneur de l'étudiant par l'API fichiers de jupyter-server, puis lance `setup.sh` / `check.sh` dans un terminal.

**Tech Stack :** Python 3.12, FastAPI 0.142.2, uvicorn 0.54.0, Jinja2 3.1.6, markdown-it-py 4.2.0 + mdit-py-plugins 0.6.1, PyYAML 6.0.3, pydantic 2.13.5, PyJWT 2.9.0, itsdangerous 2.2.0, docker 7.1.0 (SDK), git CLI ; pytest 8.3.3, httpx 0.28.1 ; Lab UI (TypeScript, sous-projet 2) ; Playwright 1.56.1.

**Spec :** [Plateforme de formation ROS 2 — Spec de design](https://claude.ai/code/artifact/e0a0510b-9545-459e-9c12-da51ca1898ba) — sections « Format d'un module, QCM et notation », « Déroulé d'une session de lab », « Stratégie de tests », sous-projet 3.

## Décisions prises avec l'utilisateur (2026-10-02)

- **Édition des formations dans la plateforme**, par un éditeur web qui enregistre dans Git (historique, retour arrière, tests avant publication). La spec prévoyait l'édition directe des fichiers dans le dépôt et repoussait l'espace formateur après la V1.
- **Un seul auteur : l'administrateur.** Pas de rôles formateur ni de relecture en V1.
- **Supports portés :** Initiation, Service, Action, URDF. Le support Nœud n'a pas été fourni : le module est rédigé à partir de ce que les supports Service et Action supposent (`first_ws`, `my_pkg`, `diff_drive_node`, pose `x, y, θ`, `move_robot`).

## Écarts assumés par rapport à la spec

- **Pas d'Astro.** Le site est rendu par le service Contenus (Jinja2). L'aperçu de l'éditeur et la page publique utilisent le même rendu, et une publication est visible immédiatement, sans étape de construction ni second outil Node à maintenir.
- **RViz et Gazebo hors V1** (spec) : le module URDF s'appuie sur `xacro`, `check_urdf`, `robot_state_publisher` et `tf2_echo` dans le terminal. La visualisation RViz devient une ouverture du cours.
- **Notes et tentatives** : la correction d'un QCM est faite par le service Contenus (les bonnes réponses ne quittent jamais le serveur), mais l'enregistrement des tentatives, des indices utilisés et des notes arrive avec le service Comptes (sous-projet 4).
- **Triche** : `check.sh` et `explication.md` sont lisibles depuis le conteneur de l'étudiant (accepté en V1 par la spec).

## Global Constraints

- Format d'un module : celui de la spec (`index.md`, `lab/`, `qcm.yaml`, `exercice/{enonce.md, setup.sh, check.sh, indices.md, solution/, explication.md}`), plus un en-tête YAML dans `index.md` (`titre`, `resume`, `duree`).
- Identifiant de module : `^[0-9]{2}-[a-z0-9-]+$` ; dossier de travail dans le lab : `~/ws/<id>` (lab guidé) et `~/ws/<id>-exercice`.
- Les bonnes réponses de `qcm.yaml` et le dossier `solution/` ne sont jamais servis au navigateur.
- Tout chemin reçu de l'éditeur est relatif au module, sans `..`, sans lien symbolique, taille max 1 Mo par fichier.
- Un module est publié seulement si : format valide, `setup.sh` puis `check.sh` échoue, `solution/` appliquée puis `check.sh` réussit, `lab/` compile avec colcon, `qcm.yaml` valide.
- Tests des modules dans `ros-lab:0.1.0`, réseau coupé, limites `free`, délai max 10 min.
- Admin : jeton JWT `role: admin` (audience `ros-academy-admin`) échangé contre un cookie de session signé (`HttpOnly`, `Secure`, `SameSite=Strict`, chemin `/admin`) ; toute requête d'écriture vérifie l'en-tête `Origin`.
- Interface en français.

## Review Focus

1. **Les réponses du QCM ne sortent jamais du serveur** : ni dans la page, ni dans l'API publique, ni dans l'aperçu. Tests : Task 4.
2. **Un module cassé n'est jamais publié** : bug absent, solution qui ne corrige pas, lab qui ne compile pas → publication refusée avec le journal des tests ; `publie` ne bouge pas. Tests : Task 3 et Task 5.
3. **Chemins de l'éditeur** : `../`, chemins absolus, liens symboliques et fichiers énormes refusés. Tests : Task 5.
4. **Espace admin** : sans cookie → redirection ; jeton étudiant (`role` absent) refusé ; POST sans `Origin` de la plateforme refusé. Tests : Task 6.
5. **Le travail de l'étudiant n'est jamais écrasé** : `lab/` copié seulement si `~/ws/<id>` n'existe pas ; Réinitialiser demande confirmation. Tests : Task 7.

│  │  ├─ store.py        ← dépôt Git : brouillon, publie, historique
│  │  ├─ testing.py      ← tests d'un module dans un conteneur ros-lab
│  │  ├─ auth.py         ← connexion admin

│  │  ├─ templates/, static/
│  └─ tests/

└─ .github/workflows/ci.yml              ← + jobs contenus et modules

### Task 1 : Format des modules et validation (`model.py`)

- `Parcours(id, titre, description, modules: list[ModuleRef(id, coef)])`, `Module(id, titre, resume, duree, cours_md, qcm, exercice)`, `Qcm(questions: list[Question(id, texte, choix, bonnes, explication)])`.
- `load_parcours(root)`, `load_module(root, id)`, `validate_tree(root) -> list[Erreur]` (messages en français, avec le fichier et la ligne si possible).
- QCM : 1 à 20 questions, 2 à 6 choix, au moins une bonne réponse, identifiants uniques.
- [ ] Tests : module valide ; chaque règle cassée produit une erreur lisible.

### Task 2 : Le parcours « ROS 2 Fondamentaux » (contenu)

Cinq modules autour du fil rouge (robot différentiel `diff_drive_node` dans `my_pkg`, workspace `first_ws`) :

| Module | Lab guidé | Exercice (situation réelle) |
|---|---|---|
| 01-initiation | workspace, package, `colcon`, CLI nœuds / topics / services / actions | `ros2 run demo_pkg talker` → *No executable found* : point d'entrée absent de `setup.py` |
| 02-noeud | `diff_drive_node` : `/cmd_vel` → pose → `/odom`, Python et C++ | le robot ne bouge pas dans la vue 2D : abonnement sur `cmd_vell` |
| 03-service | `my_interface/srv/GetPose`, serveur `get_pose` | `ros2 service call /get_pose` → *service not available* : service déclaré sous un autre nom |
| 04-action | `Goto.action`, serveur `goto` | le goal s'exécute mais finit *ABORTED* : `goal_handle.succeed()` oublié |
| 05-urdf | `my_robot_description`, URDF puis Xacro, `robot_state_publisher` | `check_urdf` échoue : un joint référence un link mal orthographié |

- [ ] Chaque module : cours porté du support, lab de départ, exercice avec `setup.sh` / `check.sh` / 3 indices / `solution/` / explication, QCM de 5 questions.

### Task 3 : Tests des modules (`testing.py`, `scripts/test_modules.py`)

- `run_module_tests(module_dir, image) -> Rapport(ok, etapes[...], journal)` : conteneur `ros-lab` jetable, réseau `none`, module monté en lecture seule.
- Étapes : `setup.sh` ; `check.sh` doit échouer ; copie de `solution/` ; `check.sh` doit réussir ; `colcon build` de `lab/` ; validation `qcm.yaml`.
- [ ] CI : job `modules` (construit `ros-lab`, teste tous les modules).

### Task 4 : Site étudiant et API publique

- Pages : `/` (parcours), `/parcours/<id>/`, `/modules/<id>/` (cours, exercice, QCM).
- Rendu : blocs de code consécutifs ```` ```python ```` / ```` ```cpp ```` groupés en onglets ; attribut `fichier=<chemin>` → bouton « Ouvrir dans le lab » (`/lab/?module=<id>&open=ws/<id>/<chemin>`).
- API : `GET /api/contenus/modules/<id>/lab` (fichiers de `lab/`), `…/exercice` (énoncé, `setup.sh`, `check.sh`), `…/indices/<n>`, `…/explication`, `POST …/qcm` (score + explications, réponses jamais envoyées avant).
- [ ] Tests : aucune bonne réponse dans le HTML ni dans l'API ; correction exacte ; `solution/` jamais servi.

### Task 5 : Dépôt Git et publication (`store.py`)

- `ContentStore(path)` : `read/write/delete(module, chemin)`, `commit(message)`, `diff_since_publish()`, `publish(runner) -> Rapport`, `history()`, `restore(commit)`.
- Publication : validation → tests des modules modifiés → `publie` avance au commit testé → `git push` si `CONTENT_GIT_REMOTE`.
- [ ] Tests (dépôt temporaire, faux runner) : publication refusée laisse `publie` intact ; chemins dangereux refusés.

### Task 6 : Espace d'administration

- `/admin/login?token=` → cookie ; `/admin/` (parcours et modules) ; `/admin/modules/<id>/` (fichiers, éditeur, aperçu, QCM en formulaire) ; nouveau module (à partir d'un modèle) ; ordre et coefficients du parcours ; « Publier » avec le journal des tests ; historique et restauration.
- [ ] Tests : accès refusés (cookie absent, jeton étudiant, `Origin` étranger) ; e2e : modifier un titre, publier, voir la page publique changer.

### Task 7 : Lab UI — module et exercice

- `?module=<id>` : copie `lab/` dans `~/ws/<id>` si absent ; panneau « Exercice » (énoncé, Commencer → `setup.sh`, Vérifier → `check.sh`, indices 1 à 3, explication après réussite) ; Réinitialiser (confirmation, renomme l'ancien dossier en `<id>.ancien-<date>`).
- [ ] Tests unitaires (fichiers jamais écrasés, analyse du code de sortie) ; e2e du module 02 dans la CI.

### Task 8 : Déploiement

- Service `contenus` dans Compose (volume du dépôt de contenu, socket Docker pour les tests de publication), routes Caddy (`/`, `/parcours`, `/modules`, `/api/contenus`, `/admin`), `scripts/mint_token.py --role admin`, README.
